## 0. The one-line thesis

**Dayflow treats leave and attendance as immutable event ledgers with a database-driven approval engine, so every balance in the system is auditable, reversible, and impossible to silently corrupt.**

Every design decision below serves that sentence. If a change makes that sentence less true, don't make it.

---

## 1. Hard rules (never violate)

1. **Balances are never stored.** `leave_balance` is computed as `SUM(delta)` from `leave_balance_ledger`. There is no balance column anywhere. Ever.
2. **Ledger and punch tables are append-only.** No `UPDATE`, no `DELETE`. A mistake is corrected by inserting a compensating row with `reason='REVERSAL'`.
3. **Approval routing lives in the database**, in `approval_chain_rules`. Never write `if (days > 5) { ... }` in application code.
4. **No ORM.** Raw parameterised SQL via `pg`. The schema is the star of this project; do not hide it behind an abstraction.
5. **No string interpolation in SQL.** `$1, $2` placeholders only. A single template literal in a query is an automatic fail on the Security criterion.
6. **Every mutating endpoint validates input with Zod before touching the DB.** No exceptions.
7. **Minimal third-party APIs.** Allowed: `pg`, `express`, `zod`, `bcrypt`, `jsonwebtoken`, `multer`, `date-fns`, `react`, `react-router-dom`, `tailwindcss`, `recharts`. Adding anything else requires a note in the PR description explaining why.
8. **Server time is the only time.** Never trust a timestamp sent by the client. Punches use `NOW()` server-side.
9. **Money and leave days are `NUMERIC`.** Never `float`. Never `REAL`.
10. **Feature freeze at 15:30.** After that: bug fixes, empty states, seed data, README only.

**Module file convention — every backend module has exactly these four files:**

- `X.routes.js` — Express router. Wiring only. No logic, no SQL.
- `X.schema.js` — Zod schemas. All input rules.
- `X.service.js` — business logic + transactions. No `req`/`res` here.
- `X.queries.js` — SQL only. Each function takes `(client, params)` and returns rows.

A route handler that contains SQL is a bug. A service that touches `req` is a bug. This four-file rhythm *is* the Modularity score.

```sql
-- 007_views_and_indexes.sql
-- The ONLY way balances are ever read.
CREATE VIEW v_leave_balances AS
SELECT e.id                AS employee_id,
       lt.id               AS leave_type_id,
       lt.code             AS leave_code,
       lt.name             AS leave_name,
       COALESCE(SUM(l.delta), 0) AS balance,
       COALESCE(SUM(l.delta) FILTER (WHERE l.reason = 'ACCRUAL'), 0) AS total_accrued,
       COALESCE(-SUM(l.delta) FILTER (WHERE l.reason = 'CONSUMED'), 0) AS total_consumed
FROM employees e
CROSS JOIN leave_types lt
LEFT JOIN leave_balance_ledger l
       ON l.employee_id = e.id AND l.leave_type_id = lt.id
WHERE lt.is_active
GROUP BY e.id, lt.id;

-- Pending work queue, used by the approvals module and the admin dashboard.
CREATE VIEW v_pending_approvals AS
SELECT s.id AS step_id, s.request_id, s.step_no, s.approver_role,
       r.employee_id, e.full_name, e.department_id,
       lt.code AS leave_code, r.start_date, r.end_date, r.day_count, r.remarks, r.created_at
FROM approval_steps s
JOIN leave_requests r ON r.id = s.request_id AND r.current_step = s.step_no
JOIN employees e      ON e.id = r.employee_id
JOIN leave_types lt   ON lt.id = r.leave_type_id
WHERE s.status = 'PENDING' AND r.status = 'PENDING';
```

## 5. The three algorithms that carry the marks

### 5.1 Applying for leave (transactional)

```
BEGIN
  1. Validate dates: end >= start, start >= today, within same calendar year
  2. day_count = business days in range, excluding weekends and `holidays`
     -> if 0, reject with 422 LEAVE_NO_WORKING_DAYS
  3. If leave type is_paid: check balance from v_leave_balances
     -> if balance < day_count, reject 422 INSUFFICIENT_BALANCE (include available in details)
  4. INSERT leave_requests  -- the EXCLUDE constraint rejects overlaps; catch 23P01 -> 409
  5. SELECT * FROM approval_chain_rules
       WHERE (leave_type_id = $type OR leave_type_id IS NULL)
         AND $days BETWEEN min_days AND max_days
       ORDER BY step_no
     -> INSERT one approval_steps row per rule
  6. INSERT notifications for each approver role
COMMIT
then: SSE broadcast 'approval:new'
```

Note step 5: adding an approval level is an `INSERT` into a rules table, not a code change. Say this out loud in the demo.

### 5.2 Deciding on a step — the concurrency showpiece

```js
await withTransaction(async (client) => {
  // Lock the request row. A second approver clicking at the same instant
  // blocks here until this transaction commits, then re-reads and sees the new state.
  const req = await client.query(
    `SELECT * FROM leave_requests WHERE id = $1 FOR UPDATE`, [requestId]
  );
  if (req.rows[0].status !== 'PENDING') throw conflict('REQUEST_ALREADY_DECIDED');
  if (req.rows[0].current_step !== step.step_no) throw conflict('STEP_SUPERSEDED');

  // ... mark step APPROVED/REJECTED, set approver_user_id, acted_at

  if (action === 'REJECT') {
    // terminal: no ledger movement at all
    UPDATE leave_requests SET status='REJECTED', decided_at=now()
  } else if (isLastStep) {
    UPDATE leave_requests SET status='APPROVED', decided_at=now()
    if (leaveType.is_paid)
      INSERT INTO leave_balance_ledger (delta = -day_count, reason='CONSUMED', ref_request_id)
    UPSERT attendance_days SET status='ON_LEAVE' for each date in range
  } else {
    UPDATE leave_requests SET current_step = current_step + 1
  }
});
```

**Cancellation** inserts `delta = +day_count, reason='REVERSAL'`. It never deletes the `CONSUMED` row. That is the whole point of the design.

### 5.3 Deriving a day's attendance status

```
For (employee, date):
  if date IN holidays            -> HOLIDAY
  elif EXTRACT(dow) IN (0,6)     -> WEEKEND
  elif APPROVED leave covers it  -> ON_LEAVE
  else:
    pair punches chronologically (IN,OUT),(IN,OUT)...; unmatched trailing IN = still in
    worked_minutes = sum of pairs
    >= 480 -> PRESENT | >= 240 -> HALF_DAY | > 0 -> HALF_DAY | 0 -> ABSENT
UPSERT into attendance_days
```

Pure function of `(punches, leaves, holidays)`. Rerunnable. Never destroys a punch.

## 6. API contract

Base `/api`. All responses JSON. Auth via httpOnly cookie.

**Success:** the payload directly, or `{ "data": [...], "page": 1, "pageSize": 20, "total": 57 }` for lists.
**Error envelope — the only error shape in the system:**

```json
{ "error": { "code": "INSUFFICIENT_BALANCE",
             "message": "You have 1.5 paid leave days available but requested 3.",
             "details": [{ "field": "endDate", "issue": "Reduce the range by 1.5 days" }] } }
```

## 7. Admin dashboard KPIs — pure SQL, no library

```sql
-- Attendance rate, last 30 days, per department
SELECT d.name,
       ROUND(100.0 * COUNT(*) FILTER (WHERE ad.status='PRESENT')
             / NULLIF(COUNT(*) FILTER (WHERE ad.status NOT IN ('WEEKEND','HOLIDAY')),0), 1) AS attendance_pct
FROM attendance_days ad
JOIN employees e ON e.id = ad.employee_id
JOIN departments d ON d.id = e.department_id
WHERE ad.work_date >= CURRENT_DATE - 30
GROUP BY d.name ORDER BY attendance_pct;

-- Monday/Friday absence pattern (window function, drives the "flagged" list)
SELECT e.full_name,
       COUNT(*) FILTER (WHERE EXTRACT(dow FROM ad.work_date) IN (1,5)
                          AND ad.status='ABSENT') AS edge_day_absences,
       COUNT(*) FILTER (WHERE ad.status='ABSENT')  AS total_absences
FROM attendance_days ad JOIN employees e ON e.id=ad.employee_id
WHERE ad.work_date >= CURRENT_DATE - 90
GROUP BY e.id, e.full_name
HAVING COUNT(*) FILTER (WHERE ad.status='ABSENT') >= 3
ORDER BY edge_day_absences DESC LIMIT 5;
```

Run `EXPLAIN ANALYZE` on the first query before and after `idx_ledger_balance_lookup` / `attendance_days(work_date,status)` and **paste both plans into the README**. That single screenshot wins the Performance criterion.

## 8. Security checklist (non-negotiable)

- [ ] bcrypt cost 10; password rule: ≥8 chars, 1 upper, 1 lower, 1 digit — enforced in Zod **and** stated in the UI
- [ ] JWT in httpOnly + SameSite=Lax cookie, 8h expiry. **Never** in localStorage
- [ ] `requireRole('HR','ADMIN')` on every admin route — checked server-side, never by hiding UI
- [ ] Ownership check on every `:id` route: an employee fetching another's `/employees/7` gets **404**, not 403 (no existence leak)
- [ ] Parameterised SQL everywhere
- [ ] Upload validation: MIME allowlist + size cap + random stored filename (never trust `originalname`)
- [ ] Rate limit `/auth/login` — 5 attempts / 15 min per email, in-memory Map is fine
- [ ] Generic login error: "Email or password is incorrect" — never reveal which
- [ ] `helmet()` + CORS locked to the Vite origin with `credentials:true`
- [ ] No secrets in git; `.env.example` committed, `.env` ignored

## 12. Tests (`node --test`) — write these six, no more

1. Balance equals `SUM(delta)` after accrual → consume → reverse
2. Approving the final step inserts exactly one `CONSUMED` row
3. Rejecting inserts **zero** ledger rows
4. Overlapping leave request raises `23P01` → mapped to 409
5. Two concurrent decides on the same step: one wins, one gets 409
6. Attendance: IN 09:00 / OUT 13:00 → `HALF_DAY`, 240 minutes

Test 5 is the one to demo live.
